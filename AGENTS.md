This is the Lakefront Digital marketing site, built with EmDash and Astro and server-rendered on Cloudflare Workers with D1 and R2. WordPress is one of the platforms Lakefront manages for clients; this site's CMS is EmDash.

## Start here

- Read [PRODUCT.md](PRODUCT.md) before changing positioning, copy, navigation or product scope. It records the audience, business model, approved claims and open questions.
- Read [DESIGN.md](DESIGN.md) before changing the interface. It records the Lakefront Digital visual system, component patterns and accessibility expectations.
- Use [README.md](README.md) for setup and feature configuration. Its template-installation instructions concern fresh installs; preserve existing CMS data when working on a populated site.
- Read [docs/plugin-sandbox.md](docs/plugin-sandbox.md) before changing EmDash dependencies or the plugin runner. It explains the temporary compatibility fixes and their removal criteria.

## Commands

```bash
pnpm install                         # Install dependencies with the pinned package manager
pnpm dev                             # Start the Astro dev server
pnpm typecheck                       # Run astro check
pnpm build                           # Build without deploying
pnpm preview                         # Preview an existing build
pnpm deploy                          # Build and deploy to Cloudflare Workers
pnpm exec emdash types               # Export types from a running EmDash site
pnpm exec emdash seed seed/seed.json --validate  # Validate the seed without changing a database
pnpm wrangler types                  # Regenerate worker-configuration.d.ts after binding changes
```

Use the pnpm version pinned in `package.json`; keep the dependency build allowances in `pnpm-workspace.yaml`. The admin UI is at `http://localhost:4321/_emdash/admin`.

`emdash-env.d.ts` is generated by the EmDash Astro integration on dev-server start. The CLI's `emdash types` command defaults to `.emdash/types.ts`; use `--url` and `--output` when targeting another instance or output file. Regenerate types after schema changes instead of hand-editing generated declarations.

## Content and product scope

Lakefront Digital is a founder-run business serving small businesses across the US from Chicago. The core offer is ongoing hosting and management, with builds, migrations and growth services leading into that relationship.

- The main conversions are **Book a consultation** (`/consultation#enquiry`) and **Start a project** (`/contact`). Service links can use `/contact?service=<slug>#enquiry` to preselect a need. There is no checkout on this site.
- Use the business voice "we" without implying staff or a team. Keep interface labels in sentence case and use the named offer **Website Consultation** consistently.
- Use only supplied prices, approved client work and supported claims. Consult `PRODUCT.md` for unresolved pricing and offer details; do not invent testimonials, metrics or credentials.
- Check the CMS before adding navigation destinations. A route or sample article in the repository does not establish that its content is ready to publish.
- For owner-authorized live content, menu and settings edits, use the site's EmDash MCP tools. Keep page copy, menus, site title and tagline in the CMS.

## Schema and seed workflow

The database owns the running site's schema and content. `seed/seed.json` supplies initial schema and optional sample content during setup; changing it and deploying does not update an already configured site. Keep the seed aligned with intended fresh installs, and apply authorized changes to an existing site through EmDash's schema/content tools.

For new blocks or breaking block versions, inspect the existing schema, add the renderer, regenerate types and verify rendering before activating the version. Preserve rendering for retained versions used by existing content and revisions. Backfill content before making an optional field required.

## Rules

- All content pages are server-rendered (`output: "server"`). No `getStaticPaths()` for CMS content.
- Image fields are objects (`{ id, src, alt }`). Render them with `<Image>` from `"emdash/ui"` (see `Photo.astro`).
- `entry.id` is the slug; `entry.data.id` is the database ULID.
- Use the taxonomy name `category` exactly as defined in the seed.
- For cached pages, pass each query's `cacheHint` to `Astro.cache.set()` in page frontmatter, then call `cachePage(Astro)` last. Layout/component hints arrive after headers are sent; `cachePage()` supplies the lifetime and the signed-in opt-out.
- Every block type in `seed.json` needs a renderer in `PageBlocks.astro`; `defineBlockComponents` enforces it. Ship a renderer before activating a new block version.
- Sanitize editor-supplied URLs with `sanitizeHref` (`cta()` and `href()` in `src/lib/text.ts` do this).

## Schema

- `pages` collection: `title`, `template` (`blocks` | `legal`), `summary`, `keywords`, `content` (blocks), `eyebrow`, `effective_date`, `body` (Portable Text). The legal fields are used only by the legal layout; the page with slug `blog` feeds the blog intro.
- `posts` collection: `title`, `excerpt`, `featured_image`, `photo` (bundled fallback), `featured` (boolean), `content` (Portable Text). `category` taxonomy (hierarchical). Bylines are optional.
- Block types (`lf_` prefix): hero, page_intro, card_grid, split, steps, service_tabs, spec_tabs, offer, cta_band, product, enquiry.
- Block text conventions: lists are one item per line; pairs are `label | value`; eyebrow items are separated with `·`.
- Menus: `primary`, `header_cta` (first item is the header button), `footer_services`, `footer_hosting`, `footer_company` (column headings come from the menu label minus `Footer:`), `footer_contact`, `footer_legal`, `search_popular`.
- Blocks aren't searchable (in full-text or AI search), so `summary` and `keywords` carry each page's search terms.

## Runtime and integrations

- Preserve `src/worker.ts` as the Wrangler entry point, its `PluginBridge` export, and the scheduled handler paired with the every-minute cron trigger.
- Keep `keep_vars: true` so deployments preserve dashboard variables such as `EMDASH_SITE_URL`. Preserve Smart Placement and observability in `wrangler.jsonc`.
- The local sandbox runner is selected with an absolute path in `astro.config.mjs`, guarded by `sandbox()`'s `LOADER` check. Retain its subrequest budget, isolate-key suffix and admin repairs until the upstream replacements are verified as described in `docs/plugin-sandbox.md`. Change the suffix when changing sandbox limits so Worker Loader does not reuse an isolate with old limits.
- AI search uses the native `aiSearch()` plugin through `AI_SEARCH`; it runs in the site Worker. Keep `urlTemplates` aligned with `/blog/{slug}` and `/{slug}`. The old registry AI Search plugin is no longer used.
- Preserve `cloudflare({ remoteBindings: false })` for local development so local seed/draft content cannot enter the production AI Search index. Public search results are checked against current published content; see `docs/plugin-ai-search.md`.
- Enquiries use `ENQUIRY_EMAIL`, `ENQUIRY_FROM` and `ENQUIRY_TO`. Keep the sender on the onboarded domain and the recipient aligned with `destination_address`. Use Cloudflare Email Sending; preserve the Google Workspace MX records by leaving Email Routing disabled.
- Preserve enquiry validation, honeypot handling, JSON responses for enhanced forms and 303 redirects for ordinary form posts. Missing email configuration logs locally and fails in production.

## Visual character

From the Lakefront Digital design system: Manrope (`--font-display`) for headings, nav, buttons and eyebrows; Source Sans 3 (`--font-body`) for body and forms. Lake Navy, Deep Water and Current Teal carry the brand; Sunset Coral is the one action colour (primary buttons). Night sections (`data-theme="night"`) flip to a navy canvas. Photos are tall, softly rounded panels.

Use navy labels on coral buttons and Deep Water for teal text at body or label size. Prefer lake textures, Chicago architecture and real work photography; client work must use approved real screenshots. Use the `-reversed` brand SVGs on navy backgrounds. See `DESIGN.md` for component details, spacing and motion.

## Customisation

Tokens are in `src/styles/tokens.css` (`@layer base`). Override them in `src/styles/theme.css`, which is unlayered and always wins. Component styles (`lf-`) are in `components.css`; layout styles (`lfw-`) in `site.css`. Fonts are configured in `astro.config.mjs`.

## Verification

- For code changes, run `pnpm typecheck`, `pnpm test` (Node 24), and `pnpm build`. Run `pnpm test:browser` against a populated local instance for interface changes; `PLAYWRIGHT_BASE_URL` selects its URL (default `http://127.0.0.1:4332`). Enquiry tests intercept submissions. `pnpm deploy` publishes the Worker.
- For seed changes, also run `pnpm exec emdash seed seed/seed.json --validate` and check that every allowed block type has a renderer.
- For interface changes, check the affected routes at desktop and mobile widths, light and night sections, keyboard focus, reduced motion and no-JavaScript behaviour. Preserve the skip link, labelled fields, ARIA state and legal print styles. Use local email simulation for form checks.
- For documentation-only changes, check referenced paths, commands and `git diff --check`; a deployment is unnecessary.

## What not to do

- Don't hard-code content that belongs in the CMS: menus, site title, tagline and page copy come from EmDash.
- Don't add a second action colour; coral is reserved for primary actions.
- Don't make block fields required on a populated site without backfilling content first.
- Don't remove the no-JavaScript paths: tabs stack, the enquiry form posts normally, the legal TOC links work.
